## 1. Что выяснено о проекте (рекогносцировка)

### 1.1. Движок сайта

| Параметр | Значение | Как выяснено |
| --- | --- | --- |
| CMS | **Diafan.CMS 7.0** | подпись сборки на странице `/admin/` |
| Префикс таблиц | `diafan_` | `config.php` |
| Версия | 7.0 (сборка адаптера 7.6.6 по версии `/adm/js/main.js`) | `config.php`, HTML |
| Админка | `/admin/` — папку задаёт `ADMIN_FOLDER` | `config.php` |
| Раздел блога | страница-оболочка + модуль `news`, URL `/news/` | админка, `diafan_site` |
| ЧПУ | `ROUTE_AUTO_MODULE = true`, `ROUTE_END = ''` | `config.php` |
| Кэш | файловый, `MOD_DEVELOPER_CACHE = false` | `config.php` |
| Хостинг | shared-хостинг, nginx + PHP 7.4, агрессивная анти-флуд защита | FTP, заголовки ответов |

### 1.2. Доступы и их реальная пригодность

| Канал | Статус | Ограничения |
| --- | --- | --- |
| FTP | ✅ работает | **жёсткий рейт-лимит**: ~1 подключение в 30-60 с, `LIST` не работает (только `NLST`/`MLSD`). Годится для деплоя и бэкапов, не для ежедневной работы |
| Админка Diafan (HTTP) | ✅ работает | рейт-лимит: после ~5-8 запросов IP блокируется на несколько минут. Не годится как ежедневный транспорт |
| MySQL снаружи (3306) | ❌ | порт открыт, но пользователь БД пускается только с localhost |
| SSH (22) | открыт | учётных данных нет |
| `config.php` по FTP | ✅ | содержит пароли в открытом виде — держите его вне веб-доступа и вне git |

> **Вывод №1.** Прямая запись в MySQL и «долблёжка» админки по HTTP — тупик из-за рейт-лимитов и закрытого MySQL. Публикация должна идти **одним запросом на статью**, а вся тяжёлая работа — на локальной машине.

### 1.3. Найденный готовый образец (важно)

В корне сайта лежит **`import.php`** — рабочий скрипт прошлого подрядчика. Он показывает проверенный паттерн работы с Diafan «изнутри»:

```php
define('DIAFAN', 1); define('ABSOLUTE_PATH', ...); include config.php; define('IS_ADMIN', 1);
include includes/{custom,developer,diafan,file}.php;
include includes/core.php; include includes/init.php;
$diafan = new Init();

DB::query("INSERT INTO diafan_rewrite (rewrite, module_name, element_id, element_type, trash, import) VALUES ('%s','%s',%d,'%s','%s',%d)", ...);
$diafan->_images->upload($id, "site", "element", 0, $tmp_path, $img_name, true, 0, "");
```

Это готовый **blueprint публикатора**: `DB::query()` с плейсхолдерами + `$diafan->_images->upload()` для корректной нарезки картинок по вариациям.

### 1.4. ⚠️ Критические находки безопасности

**Первая: открытый `import.php`.** Скрипт в корне сайта был доступен без
авторизации, и в нём перед любой проверкой выполнялось:

```php
DB::query("DELETE FROM `diafan_site` WHERE import=1;");
DB::query("DELETE FROM `diafan_rewrite` WHERE import=1;");
DB::query("DELETE FROM `diafan_images` WHERE module_name='site'");
clear_dir($_SERVER['DOCUMENT_ROOT'] . '/userfls/original');
clear_dir($_SERVER['DOCUMENT_ROOT'] . '/userfls/site/large');
clear_dir($_SERVER['DOCUMENT_ROOT'] . '/userfls/site/medium');
```

**Один GET-запрос любого человека в интернете уничтожал все изображения
раздела `site`.** Я намеренно не вызывал этот URL, чтобы не навредить;
вывод сделан по чтению кода, скачанного по FTP. Рядом лежал такой же
открытый `upd.php`.

**Вторая: публично доступный дамп базы данных.** В корне сайта лежал дамп
(2,4 МБ) — выгрузка базы другого сайта. Проверено запросом: сервер отдавал
его с `HTTP 206` и `Content-Type: application/sql`, то есть скачать мог кто угодно.

**Сделано:** `import.php`, `upd.php`, `simple_html_dom.php` и дамп удалены
с хостинга. Перед удалением каждый файл сохранён в `data/backups/<дата>/`
(восстановить можно за секунды).

## 2. Целевая архитектура

### 2.1. Принцип

> Тяжёлая работа (LLM, картинки, валидация, перелинковка) — **локально**.
> На сайт — **один HTTPS-запрос на статью**, который делает всё «изнутри» Diafan.

Это прямое следствие рейт-лимитов хостинга: чем меньше запросов, тем устойчивее система.

### 2.2. Схема

```
┌──────────────────────── ЛОКАЛЬНАЯ МАШИНА (Windows) ──────────────────────────────────┐
│                                                                                        │
│  themes.txt ──► topics.py ──► writer.py ──► linker.py ──► verify.py ──► images.py      │
│  (очередь)      (антидубль,    (LLM:          (до 4       (контракт      (обложка      │
│                  кластеры)      DeepSeek|       внутр.      HTML +        800×510)      │
│                                 Ollama)         ссылок)     AI-SEO                       │
│                                                             чек-лист)                   │
│                                                    │                                     │
│                                              registry.json (идемпотентность)             │
└────────────────────────────────────────────────────┼─────────────────────────────────────┘
                                                     │  POST JSON + base64(cover)
                                                     │  1 запрос на статью
                                                     ▼
┌──────────────────────────────── your-site.example.com ─────────────────────────────────┐
│  publisher.php  (деплой по FTP, 1 раз; секретный токен)                                 │
│    1. проверка токена / POST / размера                                                   │
│    2. бутстрап Diafan: config.php + includes/init.php + new Init()                       │
│    3. INSERT diafan_news  (name, anons, text, cat_id, site_id, created, act, SEO-поля)   │
│    4. INSERT diafan_rewrite   (ЧПУ /news/<slug>)                                         │
│    5. $diafan->_images->upload()  → 800×510 в userfls/news/{smalla,large}/                │
│    6. сброс кэша                                                                          │
│    7. ответ JSON {ok, id, url}                                                            │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.3. Почему именно так

| Альтернатива | Почему не подходит |
| --- | --- |
| Прямая запись в MySQL снаружи | хостинг не пускает по IP; плюс обход кэша и индексов Diafan |
| Автоматизация админки (Playwright/Selenium) | 5-8 запросов на статью → блокировка IP; ломается при обновлении CMS |
| Публикация через REST API, как в других CMS | у Diafan нет REST API |
| Весь конвейер на сервере (cron + PHP) | нет GPU для картинок, нет локальных моделей, отладка вслепую. **Оставляем как опцию** (см. §6) |
| FTP-заливка HTML-файлов | статья — запись в БД, а не файл |

## 3. Пайплайн одной статьи

1. **Тема** — берётся из `themes.txt`; проверяется на дубль по `catalog.json` (нормализованное сравнение заголовков + шинглы).
2. **Кластер** — теме сопоставляется коммерческая страница-цель (каталог разделов собирает `catalog.py`) и 3-6 «сестринских» статей.
3. **ЧПУ** — короткий slug (2-6 символов, как принято на сайте: `inu`, `ek`, `ohrana`), проверка занятости по `catalog.json` и `registry.json`.
4. **Текст** — LLM по `prompts/writer.md` возвращает строгий JSON:
   `{name, anons, text, title_meta, descr, keywords}`.
   - `name` — короткий H1, как у существующих статей сайта.
   - `title_meta` — длиннее, с двоеточием (как на сайте: «…: как строится работа с личным менеджером»).
   - `anons` — одна строка-подзаголовок для карточки в списке.
   - `text` — HTML строго по контракту §1.5. **Ссылок не ставит** — их добавляет linker.
5. **Перелинковка** — детерминированно, кодом: 3-4 ссылки, каждая в **своём H2-блоке**, анкор 2-5 слов, вплетён в существующую фразу, минимум одна — на коммерческую страницу услуги (перенос и развитие `linker.py`).
6. **Валидация** — блокирующие проверки (см. §4): теги и классы, наличие `analytics-table`, `faq-section`, лида, чисел, цен, отсутствие хеджей и превосходных степеней, распределение ссылок по секциям, уникальность.
7. **Обложка** — 800×510 JPEG + `alt`/`title` из `name`.
8. **Публикация** — один POST в `publisher.php`; запись в `registry.json`; тема удаляется из `themes.txt` **только после успеха**.
9. **Пост-проверка** — через паузу GET URL статьи, сверка H1 и наличия картинки (не фатально).

## 4. Промпт писателя: что в него войдёт (из исследования AI SEO)

Исследование (`docs/ai-seo-research-2026.md`) дало жёсткие, подтверждённые требования. Ключевое из них:

**Что подтверждено и попадает в промпт:**
- Google (15.05.2026) и Яндекс («ЭПОС») официально: **отдельных требований для AI-поиска нет**, работает обычное ранжирование. Значит — не выдумываем «AI-магию», делаем сильный контент + топ-10.
- **Answer-first**: первые 100 слов дают прямой ответ с числом; ~40 % цитат AI Overviews берутся из первых 100 слов страницы.
- **H2 = подвопрос клиента**, первый абзац под каждым H2 — 40-70 слов с прямым ответом (официальная механика Алисы AI: разбивка на подвопросы и смысловые блоки).
- **Цена/тариф/вилка** — сильнейший фактор цитирования (SIGIR 2026, OR ≫ 10 000).
- **Свежесть**: видимая дата публикации и обновления.
- **Числа с источником** — единственный метод из Принстонской GEO, который **реплицировался** на всех платформах (Claude +120 %, ChatGPT +56 %, Perplexity +37 %, Google AI Mode +21 %).
- **Уверенные формулировки** вместо хеджей («возможно», «как правило») — OR 2,67-754.
- **Не commodity**: обязателен собственный неповторяемый элемент (кейс с числами, замер, обоснованное несогласие) — Google называет это фактором №1.
- **Таблицы сравнения** вариантов, списки 3-7 пунктов, самодостаточные предложения.

**Что в промпт НЕ попадёт (мифы):**
- «чанкинг» под AI, llms.txt, keyword stuffing (даёт результат **ниже** baseline), schema как рычаг AI-цитирования, обилие цитат и «according to», требование идеальной длины.
- Конкретное «оптимальное» число внутренних ссылок — не подтверждено; остаёмся на требовании «до 4 ссылок на статью».

### ⚠️ Риск, который надо назвать прямо

План «2 статьи в день» = ~730 статей в год. Google **прямо** квалифицирует генерацию страниц под вариации запросов как *scaled content abuse*, а корреляция числа страниц с AI-видимостью ≈ 0,194 (почти ноль). При этом 80-90 % AI-цитат приходят из топ-3/топ-10 органики.

Практический вывод: **2 статьи в день допустимы только при условии, что в каждой есть собственный неповторяемый элемент.** Если уникальных данных нет — часть «слотов» лучше отдавать **обновлению существующих статей** (`dateModified`), что подтверждённо усиливает цитирование по фактору свежести.

Для этого нужен контур собственных данных: сроки, ставки, статистика по типовым операциям. Это отдельная задача, и её стоит начать **до** масштабирования.

## 5. Изображения: рекомендация

Факты: планка низкая (обычный сток, без брендинга), нужен ровно один размер 800×510, изображения **не влияют** на попадание в AI-ответы (влияет только наличие релевантной картинки и корректный `alt`).

**Рекомендация: автоматизировать, но с подстраховкой.**

| Приоритет | Источник | Плюсы | Минусы |
| --- | --- | --- | --- |
| 1 | **Стоковый API (Pexels/Unsplash)** — подбор по ключевым словам темы | Совпадает с текущим видом 1:1, реалистичные B2B/производственные кадры, бесплатно, коммерческая лицензия, ~1 с | Фото могут повториться у конкурентов |
| 2 | **Локальная SDXL** (8 ГБ VRAM, torch+cu121) | Уникальные картинки под тему | Нужно скачать ~7 ГБ модели + `diffusers`; 30-60 с/картинка; артефакты на людях и руках |
| 3 | **Pillow-шаблон** (брендовый фон + заголовок) | Детерминированно, всегда в фирменном стиле | Отличается от текущего вида сайта (сейчас текста на обложках нет) |

Предлагаемый режим: **автогенерация по умолчанию (сток → при неудаче SDXL), кроп/ресайз ровно в 800×510 через Pillow, `alt`/`title` из заголовка.** Плюс флаг «поставить статью в очередь на ревью картинки» — публикуется сразу, но в отчёте помечается, что обложку можно заменить рукой в один клик.

## 11. Находки, сделанные уже в ходе внедрения

Эти вещи не видны из документации и стоили отдельных итераций — фиксирую,
чтобы не наступить дважды.

### 11.1. Главная ловушка: целое число в ENUM-колонку MySQL

Первая боевая публикация записалась как **черновик** и отдавала 404, хотя в
payload было `act: 1`. Причина: MySQL трактует целое число в ENUM-колонке как
**индекс значения**, а не как само значение.

| Что передали | Как понял MySQL | Результат |
| --- | --- | --- |
| `act = 1` (int) | индекс 1 → первый член `enum('0','1')` | записалась `'0'` — черновик |
| `noindex = 0`, `map_no_show = 0`, `access = 0` (int) | индекс 0 — не существует | записалась пустая строка |

**Решение:** в `pub_insert()` / `pub_update()` тип колонки берётся из
`SHOW COLUMNS`, и enum-поля **всегда квотируются**. Плюс `DB::query()`
в Diafan при ошибке молча возвращает `false`, поэтому INSERT/UPDATE идут
напрямую в `DB::$backend->query()` внутри `try/catch` — так виден текст ошибки.

### 11.2. Пост-проверка через HTTP почти всегда откладывается

Один POST публикации уже расходует бюджет запросов, поэтому немедленный GET
страницы почти всегда упирается в блокировку. Проверка сделана откладываемой:
фиксируется статус `deferred`, а догоняет её `check.py` отдельным запуском.

### 11.3. Блокировка наступает после 3–5 запросов

Это не «медленный хостинг», а активная анти-флуд защита: IP перестаёт
отвечать на несколько минут. Отсюда жёсткое правило архитектуры —
**один запрос на статью** и пауза между статьями в `publish.ps1`.

### 11.4. CTA-блок не нужно верстать

В теле статьи достаточно тега
`<insert name="show_form" module="feedback" template="ask" site_id="<id страницы формы>">` —
Diafan сам разворачивает его в готовую форму со всеми скрытыми полями
(`form_tag`, `tmpcode`, `site_id`). Проверено на живой публикации.

### 11.5. Внутренние ссылки: два формата, выбран абсолютный URL

Diafan умеет внутренний формат `map:lang_id=1;module_name=site;element_id=…`,
и он встречается в существующих статьях. Но у него опасное поведение:
**несуществующий element_id молча превращается в ссылку на главную** (такая
битая ссылка реально встречается в одной из статей сайта). Поэтому линкер
ставит обычные абсолютные URL — их можно
проверить и они не деградируют молча.

### 11.6. Изображения: обе вариации остаются 800×510

`smalla` — resize до 800×800, `large` — до 1200×1200, но Diafan **не
увеличивает** картинку. Поэтому источник ровно 800×510 даёт одинаковый файл
в обеих папках — ровно как у существующих статей (это и объясняет, почему
`smalla` и `large` на сайте побайтово совпадают).

### 11.7. Openverse не подходит для российского B2B

Как источник без ключа проверялся Openverse (CC0/public domain). Индекс
состоит в основном из работ госорганов США: по запросу об охране труда
приходят кадры с вертолётом армии США. Провайдер оставлен в коде, но
выключен по умолчанию (`config.images.allow_openverse = false`).

### 11.8. Мусор в дереве сайта

В `diafan_rewrite` встречаются «осиротевшие» записи новостей без живых
элементов (адреса вида `news/<slug>`, которых нет среди статей) — они дают 404.
Отдельно бывает legacy-страница `diafan_site` с адресом внутри `/news/`,
дублирующая статью блога. Каталог разделов такие адреса отсеивает, но
владельцу сайта стоит их почистить.

### 11.9. Планировщик Windows: две ловушки, обе роняют задачу молча

Задача падала с кодом 1, и в логе не было ни строки — то есть скрипт
не доходил даже до первой записи.

1. **BOM.** Скрипты сохранены в UTF-8 **без** BOM (так их пишет обычный
   редактор). Планировщик запускает `Windows PowerShell 5.1`, который без
   BOM читает файл как ANSI: русские строки превращаются в кракозябры,
   кавычки «разъезжаются», парсер падает с `TerminatorExpectedAtEndOfString`.
   Из интерактивного `pwsh` 7 ровно тот же файл работает — поэтому ошибка
   не видна при ручном запуске. **Решение:** все `.ps1` пишутся с BOM,
   а отдельный скрипт проверяет и парсинг в хосте 5.1, и наличие BOM.

   Дополнительно задачи Планировщика переведены на **PowerShell 7 (`pwsh`)**:
   он читает UTF-8 без BOM корректно и даёт предсказуемую работу с дочерними
   процессами. Хост выбирается функцией `Get-PowerShellHost` (pwsh, иначе
   `powershell.exe`), поэтому на машине без PowerShell 7 всё продолжит
   работать. Запуск pwsh из Планировщика проверен — задача завершается с
   кодом 0, несмотря на то что он установлен как Store-приложение
   в `WindowsApps`.

2. **Взаимная блокировка при захвате вывода.** Попытка читать и stdout,
   и stderr дочернего процесса через `ReadToEnd()` вешает задачу навсегда:
   если один буфер переполнится, дочерний процесс встанет на записи в него,
   а родитель будет ждать закрытия другого. Задача висела в статусе
   `Running` до снятия вручную. **Решение:** вывод не захватывается вообще —
   лог пишет сам Python (`--log`), PowerShell читает только код возврата.
   Общий модуль логирования — `src/logsetup.py`.

### 11.10. Полная перегенерация статьи не работает — нужны точечные правки

Первая версия цикла автоповтора просила модель «переписать статью целиком,
устранив замечания». На практике это осциллирует: попытка 2 чинит замечание
из попытки 1 и ломает ранее выполненное требование. Реальный прогон:

| Попытка | Что произошло |
| --- | --- |
| 1 | 2116 слов, ошибка: «нет чисел в разделе» |
| 2 | **1348 слов** — модель сократила текст; новая ошибка: объём |
| 3 | 1936 слов, но появился заголовок «Заключение» |

**Решение:** модель получает свою предыдущую версию в JSON и список
замечаний, и должна исправить **только их**, сохранив остальное и объём.
Тот же прогон после изменения: попытка 1 — 2232 слова и не хватило ссылок;
попытка 2 — **2284 слова**, 3 ссылки в разных разделах, финал пройден.

Дополнительно объём стал блокирующим требованием (недобор ниже 90 % от
минимума), иначе сокращённая статья уходила в публикацию.

### 11.11. Линкер: мягкий поиск без потери смысла

Точного совпадения анкора в тексте часто нет — статья про квоты давала
всего 2 ссылки из 3. Добавлен трёхуровневый поиск: точная формулировка →
значимые слова с пропусками до 3 слов → обратный порядок для двухсловных
анкоров.

При этом всплыла семантическая ошибка: анкор «аренда ит-персонала» после
разбиения по дефису превращался в «аренда» + «персонала», и мягкий поиск
привязывал обычную фразу «арендой персонала» к странице ИТ-услуг.
**Исправлено:** дефис считается частью слова, а мягкие шаблоны не
применяются к анкорам, состоящим только из родовых слов («аренда»,
«персонал», «услуги»). Проверяется тестом
`test_linker_does_not_link_generic_to_specific`.

### 11.12. Устойчивость очереди тем

43 темы — это три недели при двух статьях в день. Добавлен генератор
`src/topics.py`: он получает список уже написанного и стоящего в очереди
и предлагает только самостоятельные темы (проверка на дубли по шинглам
и по коэффициенту похожести). Темы-перестановки ключевых слов намеренно
не генерируются — Google прямо квалифицирует это как scaled content abuse.
При остатке меньше 10 тем `run_one.py` печатает предупреждение.

### 11.13. Полный отказ от CMD

Изначально в проекте было три точки, тянувшие CMD:

| Что было | Почему плохо | Чем заменено |
| --- | --- | --- |
| `publish.bat` — обёртка для запуска | Лишний процесс CMD в цепочке | Удалён; запуск идёт из PowerShell напрямую: `.\publish.ps1` |
| `chcp 65001` для кодировки | `chcp` — внешняя утилита `chcp.com`, то есть снова CMD | `Initialize-Console` в `ps-common.ps1`: кодировка ставится через `System.Text.UTF8Encoding` |
| Задачи запускали `powershell.exe` (5.1) | Легаси-хост: ANSI по умолчанию, проблемы с UTF-8 | `Get-PowerShellHost`: сначала `pwsh` (PowerShell 7), при отсутствии — `powershell.exe` |

Общий код вынесен в `ps-common.ps1` (подключается через dot-source):
настройка кодировки, выбор хоста, поиск `python.exe` вне зависимости
от PATH и запись лога. Лог пишется через `[System.IO.File]::AppendAllText`
с `UTF8Encoding($false)` — `Add-Content -Encoding UTF8` в PowerShell 5.1
добавляет BOM при создании файла и не добавляет при дозаписи, из-за чего
лог получается смешанным.

Проверено: во всём проекте не осталось ни `.bat`/`.cmd`, ни вызовов
`chcp`/`cmd.exe`; Python внешние процессы не запускает вовсе (только
`requests` и `ftplib`).

### 11.14. Изображение статьи: справа от текста, а не под статьёй

Ядровый шаблон `modules/news/views/news.view.id.php` выводит блок `_images`
**после** `</div>` от `_text`, поэтому картинка оказывалась под статьёй.

При этом в CSS сайта уже были оба сценария, и разница только в месте вывода:

| Положение `_images` | Действующее правило | Результат |
| --- | --- | --- |
| Снаружи `_text` | `.section-d_news_id ._images { float:none; margin:0 0 20px 0 }` | картинка под статьёй |
| Внутри `_text` | `.section-d_news_id ._text ._images { float:right; margin:0 0 20px 30px; max-width:50%; border-radius:12px; box-shadow:… }` | справа с отступами |

Селектор с тремя классами специфичнее, поэтому внутри `_text` выигрывает
именно правило обтекания.

**Решение:** переопределение `custom/my/modules/news/views/news.view.id.php` —
копия ядрового шаблона, в которой `_images` перенесён внутрь `_text` и
выводится перед текстом. Отличие от ядрового шаблона ровно одно — место
вывода картинки; всё остальное (дата, счётчик, теги, рейтинг, навигация,
комментарии, похожие) оставлено как есть. В репозиторий файл не положен:
это копия кода CMS, а не наш код (см. `server/README.md`).

Почему переопределение, а не правка ядра: Diafan сначала ищет шаблон в
`custom/<модуль>/`, и такой файл не затрётся при обновлении CMS. Механизм
проверен на существующем `custom/my/modules/site/views/site.view.show_images.php`,
который точно так же перекрывает ядровый.

Никаких правок CSS не потребовалось, обтекание отключается на мобильных
штатным медиазапросом сайта.

### 11.16. Переобход в Яндексе: готовый токен подошёл

После публикации статья отправляется на переобход через API
Яндекс.Вебмастера. Готовая реализация нашлась в соседнем проекте
(`content-pipeline_gpt/recrawl.py`), но главное — **отдельный API создавать
не потребовалось**.

Домен достаточно один раз подтвердить в аккаунте Вебмастера — отдельного
API-приложения не требуется. Токен с доступом к Вебмастеру лежит в `.env`
этого проекта, чтобы не зависеть от чужой папки:

```
GET  /user/{id}/hosts   ->  verified=True, host_id=https:<домен>:443
```

Эндпоинты:

```
GET  /user                                   -> user_id
GET  /user/{id}/hosts                        -> host_id
POST /user/{id}/hosts/{hid}/recrawl/queue    {"url": "..."}
```

Две оптимизации против исходной реализации:

1. **Кэш идентификаторов.** `user_id` и `host_id` сохраняются в
   `data/webmaster.json`, поэтому на статью уходит один запрос вместо трёх.
2. **Переобход не роняет публикацию.** Сбой Вебмастера (нет сети, истёк
   токен, исчерпана суточная квота) не отменяет уже опубликованную статью:
   в реестре остаётся пустая отметка `recrawl_at`, а ссылку догоняет
   `python src\recrawl.py --pending`.

Отметка `recrawl_at` в `data/registry.json` пишется только тем ссылкам,
которые Вебмастер реально принял.

### 11.17. Анонс блога в каждой статье: три ошибки на пути к фиксу

**Симптом.** Вступительный текст страницы-оболочки «Блог» выводился
в начале каждой статьи.

**Источник** (проверено запросом, а не догадкой): текст лежит в поле
`anons1` страницы-оболочки «Блог» (`diafan_site`). Шаблон
`custom/my/themes/site.php` выводит его тегом `<insert name="show_anons">`,
а страница «Блог» служит оболочкой и для списка, и для статей — поэтому
анонс попадал на все страницы раздела.

#### Ошибка 1: сломал сайт правкой в шаблоне

Первая попытка — обернуть вывод в шаблоне условием на PHP:

```php
echo $this->htmleditor('<insert name="show_anons">');   // ← fatal
```

Результат: **HTTP 500 на страницах сайта**.
`Uncaught Error: Call to undefined method Parser_theme::htmleditor()`.
В шаблонной теме `$this` — это `Parser_theme`, а не контроллер модуля,
и метода `htmleditor()` у него нет.

Сайт восстановлен из бэкапа за минуту (`deploy.py backup` перед правкой
себя оправдал). **Правило: перед любой правкой шаблона — бэкап.**

#### Ошибка 2: `<insert>` внутри `if` не работает

Разбор `includes/parser_theme.php` показал порядок обработки:

```php
if($php) { $text = $this->php_in_theme($text); }   // 1. сначала исполняется PHP
...
$regexp = '/(<insert(.*?)>)/ims';                  // 2. потом разбираются insert-теги
```

PHP исполняется **до** разбора вставок, а вставки потом заменяются
безусловно — это замена текста, а не код. Значит конструкция

```php
<?php if ($cond): ?> <insert name="show_anons"> <?php endif; ?>
```

не даёт никакого эффекта: тег отрендерится в любом случае.

#### Ошибка 3: неверный признак страницы

`$this->diafan->_site->module` **не различает** список и статью — на обоих
там `news`. Первая версия фикса по этому признаку убрала анонс и со списка
блога тоже, что не требовалось.

Настоящий признак дала таблица ЧПУ — снят диагностикой (временная запись
окружения в файл, чтобы обойти кэш страниц):

```
rewrite='news'          module_name='site'  ← список блога
rewrite='news/<slug>'   module_name='news'  ← статья
```

#### Рабочее решение

`<insert name="X">` без атрибута `module` ищет файл `themes/functions/X.php`
через `Custom::path`, поэтому кастомная тема может переопределить вставку.
Фикс сделан в `custom/my/themes/functions/show_anons.php`: модуль текущего
адреса берётся из `diafan_rewrite`, и анонс выводится везде, кроме адресов,
принадлежащих модулю `news`.

```php
$anons_module = (string) DB::query_result(
    "SELECT module_name FROM {rewrite} WHERE rewrite='%s' AND trash='0' LIMIT 1",
    trim((string) parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH), '/')
);
if ($anons_module !== 'news') { /* вывести анонс */ }
```

Проверено на шести адресах: статьи — анонса нет; список и пагинация
(`/news`, `/news/page2`) — анонс на месте; страница услуг и главная — 200,
без изменений.

### 11.18. Обложки: автоподбор отключён в пользу ручной генерации

Стоковые фото оказались непригодны — кадры выходили неудачными и
провокационными. Решение: **автоподбор выключен** (`config.images.provider
= "none"`), картинки готовятся вручную (генерация в Qwen) и прикрепляются
скриптом. Провайдер переключается одной строкой в `config.json`.

Что изменилось:

| | |
| --- | --- |
| Статья публикуется | с нейтральной фирменной плашкой-заглушкой |
| Своя картинка крепится | `python src\set_cover.py --id N --file путь` |
| Пакетно | `python src\set_cover.py --from-dir covers` — имена файлов = слаги |
| Размер | готовить не нужно: `to_cover()` обрежет в 800×510 по центру |

Заглушка выбрана вместо «публиковать без картинки»: карточка статьи в списке
блога остаётся целостной, а плашка сразу показывает, что обложка не готова.
В реестре такие статьи помечены `image_provider = "pillow_brand"`, свои —
`"manual"`, поэтому `--list` и `--from-dir` точно знают, что требует замены.

Код провайдеров Pexels и Openverse сохранён: чтобы вернуть автоподбор,
достаточно поменять `provider` в `config.json` на `auto`. Ключ Pexels
берётся из `.env`.
